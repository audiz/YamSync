# Performance, Memory & Architecture Guidelines (Kotlin Multiplatform)

Данные правила обязательны для соблюдения во всём проекте (Android, iOS, Desktop/JVM) во избежание утечек памяти, зависаний интерфейса (UI Freezes) и деградации производительности.

---

## 1. Защита от N+1 (Батчинг сетевых и файловых операций)

* **Сетевой N+1**:
  - ❌ **Запрещено**: Отправлять сетевые запросы в цикле для каждого отдельного элемента (например, `trackIds.forEach { getTrackDetails(it) }`).
  - ✅ **Обязательно**: Использовать батчинг. В Яндекс Музыке метаданные треков запрашиваются пачками (чанками по 30–50 штук) через `repository.getTracksDetails(chunk)`.
* **Дисковый N+1**:
  - ❌ **Запрещено**: В цикле по сотням треков выполнять отдельные вызовы `File.exists()` или читать теги/длительность файлов синхронно.
  - ✅ **Обязательно**: Сканировать файловую структуру один раз, собирать быстрый индекс (`Set<String>` путей или хешей) и сопоставлять данные в памяти со сложностью $O(1)$.

---

## 2. Алгоритмическая гигиена и коллекции ($O(N)$ вместо $O(N^2)$)

* **Поиск и фильтрация связей**:
  - ❌ **Запрещено**: Вложенный линейный поиск `list1.filter { item -> list2.any { it.id == item.id } }` ($O(N \times M)$).
  - ✅ **Обязательно**: Предварительно преобразовывать вторую коллекцию во множество:
    ```kotlin
    val targetIds = list2.map { it.id }.toSet()
    val filtered = list1.filter { it.id in targetIds } // O(N + M)
    ```
* **Конкатенация списков**:
  - Избегать `list = list + item` внутри циклов. Использовать `MutableList`, `buildList { ... }` или единичное обновление в конце пакетной операции.
* **Кооперативное прерывание в циклах (`yield`)**:
  - При обработке тяжёлых коллекций (более 100 элементов) в корутинах вызывать `yield()` каждые 30–50 элементов, чтобы не блокировать пул диспетчера.

---

## 3. Корутины, многопоточность и отмена задач

* **Проброс `CancellationException`**:
  - ❌ **Запрещено**: Проглатывать отмену корутины в общих блоках `catch (e: Throwable)` или `catch (e: Exception)`. Это ломает механизм отмены задач, порождая "зомби-корутины".
  - ✅ **Обязательно**:
    ```kotlin
    try {
        doWork()
    } catch (e: CancellationException) {
        throw e // Обязательно пробрасывать дальше!
    } catch (e: Exception) {
        // Обработка бизнес-ошибок
    }
    ```
* **Запрет слепого опроса (Busy-wait Polling)**:
  - ❌ **Запрещено**: Циклы вида `while (condition) { delay(50); check() }` для ожидания состояния.
  - ✅ **Обязательно**: Использовать реактивные примитивы: `StateFlow`, `SharedFlow`, `Channel` или коллбэки завершения.
* **Ограничение параллелизма (Concurrency Throttling)**:
  - Не запускать неограниченное число параллельных загрузок (`items.forEach { launch { ... } }`).
  - Ограничивать параллелизм через `Semaphore(permits = 3..5)` или `flatMapMerge(concurrency = 3)`.
* **Мутации состояния коллекций**:
  - Коллекции UI-состояния (`loadedTracks` и др.) должны изменяться строго в главном потоке (Main Dispatcher) либо защищаться `Mutex`. Фоновые воркеры на `DispatcherIO` должны отдавать неизменяемые списки (`List<T>`).

---

## 4. Zero Main-Thread I/O & Защита от UI-фризов

* **Главный поток (UI Main Queue) — только для рендеринга**:
  - Любые операции с диском (`File`, `NSFileManager`), парсинг JSON (`decodeFromString`), распаковка архивов и чтение тегов аудио строго изолируются:
    ```kotlin
    withContext(DispatcherIO) {
        // тяжёлый I/O или парсинг
    }
    ```
* **Потоковая передача данных вместо полной загрузки в память**:
  - ❌ **Запрещено**: Читать аудиофайлы целиком в массив байт (`readBytes()`). Файл 30–70 МБ в куче на iOS вызывает быстрое срабатывание Jetsam / Memory Pressure Termination.
  - ✅ **Обязательно**: Стриминг и копирование через потоки/каналы фиксированными буферами (64–256 КБ).

---

## 5. Архитектура кеширования и целостность данных

* **Каноническая изоляция ключей кеша (`cacheKey`)**:
  - ❌ **Запрещено**: Использовать только заголовок экрана (`title`) в качестве имени кеш-файла. Это вызывает коллизии между разными артистами с одинаковыми именами или одноимёнными плейлистами.
  - ✅ **Обязательно**: Ключи кеша должны быть строго детерминированными и уникальными: `artist_${artistId}`, `playlist_${uid}_${kind}`, `album_${albumId}`, `likes`, `history`.
* **Валидация кеша по авторитетным данным сервера**:
  - Локальный кеш служит исключительно быстрым офлайн-превью.
  - При получении свежего авторитетного списка `allTrackIds` от API кешированные данные обязаны фильтроваться: любые треки, отсутствующие в `allTrackIds`, немедленно удаляются из памяти и дискового кеша.

---

## 6. Compose Multiplatform: Рекомпозиция и списки

* **Стабильные ключи в списках**:
  - Всегда указывать `key` в `LazyColumn` / `LazyRow`:
    ```kotlin
    items(items = tracks, key = { it.id }) { track ->
        TrackItemCard(track = track, ...)
    }
    ```
* **Изоляция высокочастотного состояния (High-Frequency State)**:
  - Не читать состояние миллисекунд плеера (`playbackPositionMs`) или скролла на самом верхнем уровне экрана, чтобы микросекундные обновления не рекомпозировали весь экран каталога. Изолировать подписчиков внутри конкретных компонентов (`PlayerBar`, `ProgressSlider`).
* **Мемоизация лямбд и тяжёлых вычислений**:
  - Использовать `remember` для объектов и коллбэков, не меняющихся между кадрами.
  - Использовать `derivedStateOf` для производных фильтров и проверок условий.
